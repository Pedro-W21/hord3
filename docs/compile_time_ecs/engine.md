# The Hord3 compile-time ECS engine

We will assume you now have one or more fully implemented entity archetypes, you can now assemble them into a fully-featured multi-archetype game logic backend.

However, you cannot directly create a game logic backend/engine, you still need a world for the entities to exist in at least.

## Defining a World

The world is defined by implementing this trait defined in `hord3::game_engine::world`

```rust
pub trait World<ID:Identify>: Sized + Sync + Send + Clone {
    type WE:WorldEvent<Self, ID>;
    type RB:RenderingBackend;
    fn update_rendering(&mut self, data:&mut <Self::RB as RenderingBackend>::PreTickData);
}
```

This may look similar to implementing both an entity and a component, this is because the mechanisms of the world are similar.

However, here only correctly implemeting the associated time `WE` is necessary, as both other trait entries are currently obsolete and will be reworked in a future release (for a valid placeholder of `RB`, use `TestRB` from the testing files).

here is the `WorldEvent<W:World<ID>, ID:Identify>` trait :

```rust
pub trait WorldEvent<W:World<ID>, ID:Identify>: Sized + Sync + Send + Clone {
    fn apply_event(self, world:&mut W);
    fn get_source(&self) -> Option<ID>;
    fn should_sync(&self) -> MustSync;
}
```

It is mostly semantically identical to `ComponentEvent`, without a target since it is implicitly always the world passed for application of events.

To render the world, it is now necessary to implement another trait :

```rust
pub trait Renderable<RB>:Sized + Sync + Send {
    fn do_render_changes(&mut self, render_data:&mut RB);
}
```

This is functionally equivalent to the per-archetype rendering traits generated by macro, only that the World type doesn't need a special macro per world. This function is what will be called to update the world's rendering in the right engine task.

Now, once the world is fully implemented, you can move on to actually creating an engine with all the parts accumulated thus far.

## Creating an engine

We will only go over the automated way to create an engine using macros, using an example from test files :

```rust
#[derive(GameEngine, Clone)]
#[rendering_engine = "Vectorinator"]
#[tick_stages = 3]
pub struct SinglePEngine {
    ent1:CoolEntity,
    world:SinglePWorld,
    #[extra_data]
    extra_data:SingleExtraData
}
```

Note : the `World`-containing field must always be named `world`, and there can only be one

### macro attributes

#### `#[rendering_engine = "..."]`

This is used on the type-definition level to define which rendering engine this engine will be associated with it requires the following : 
- the rendering engine is accessible in the current namespace
- the rendering engine must have a `get_write() -> RBW` method to get a writeable version of the rendering engine 
- the archetypes all have an implementation of their respecting rendering traits with this engine's writeable version as a rendering backend
- the world has an implementation of `Renderable<RBW>`

for a "writeable rendering engine" example, the `Vectorinator` rendering engine has a seperate type named `VectorinatorWrite` with exclusive locks on all rendering data for this purpose. For other engines like `MantleHandler`, `MantleHandler` is its own writeable type.

#### `#[rendering_engine_generic = "..."]`

This is used on the type-definition level and not seen here, but for rendering engines taking generics in their definition this is how you add them. Only one can be added at this time.

#### `#[tick_stages = N]`

This is used on the type-definition level once in order to set the number of different stages in a tick, the default if not specified is 2 (This was found to be the minimum reasonable number to easily implement collisions between entities and with the world). The derive macro will panic if N is <= 0, but it can be any `usize` value >= 1, in theory. In practice, since each stage requires a seperate function and will increase code generation, I would expect the limit to be closer to thousands than the `usize` limit.

#### `#[extra_data]`

this is used on a field that implements `Clone + Send + Sync`, in order to carry into tick stages "extra data" not beholden to any of the more heavy trait definitions of entity archetypes or worlds. This can be useful to link the game engine with the default audio engine in an ergonomic way for example. However, this data is not synced at all in a multiplayer context, so it must not contain any multiplayer-critical data.

#### `#[do_multiplayer]`

This is used on the type-definition level to implement multiplayer on the engine. This will add 7 task IDs for multiplayer-only engine tasks, which will be explained later.

#### `#[not_multiplayer]`

This is used on any of the entity archetype fields in a multiplayer context in order to signal that this entity archetype is not to be taken into account for multiplayer, so no automatic correction between server and client, no syncing.

#### `#[not_rendered]`

This is used on any of the entity archetype fields in order to skip them during the rendering update task, as some archetypes may not need to be rendered. A non-renderable archetype must always be marked with this, otherwise compilation will fail.

### Tick stage functions

In order for the macro to compile, it needs all tick stage functions in the same namespace, they are defined like so in this example :

```rust
// "i" in "stage_i" is supposed to take the stage number
pub fn stage_i<'a>(turn:EntityTurn, id:EntityID, reader: &CoolEntityVecRead<'a, SinglePEngineTID>, world_read: &WorldComputeHandler<'a, SinglePWorld, SinglePEngineTID>, extra_data:&SingleExtraData) {
    // Your tick stage here
}
```

stage numbers start from 0, this is to provide some consistency with their task IDs.

The first argument is of type `EntityTurn`, an enum created by the macro in order to dictate which entity archetype is currently being iterated on in this stage, its values are named after the field names for the entity archetypes of the corresponding engine, here :

```rust
pub enum EntityTurn {
    ent1,
}
```

The second argument is of type `EntityID`, which is `usize`, and designates the index we are currently at on the component vectors for the entity archetype described by the first argument.

There are then as many `&{archetype name}VecRead` arguments as there are declared entity archetypes, these are read-only views into those archetypes component vectors and event tunnels.

This is followed by a `&WorldComputeHandler<'a, World, ID>` argument, providing a read-only view into the current world state and a world event tunnel.

Then, if one was defined, a read-only view into the extra data type provided.


Technically, not all stage functions need to perform work on all entities, or any kind of work at all. Since stage functions are only invoked if their corresponding stage task ID is invoked, if you're unsure of how many you need it's easy to add more or too many for prototyping and then scale that back later to the correct amount.

### Engine task IDs

using this derive macros, the engine will have the following task IDs :

- 0 : applies all events [single-threaded]
- 3 : update all rendering [single-threaded]
- if multiplayer is activated :
    - 10 : handle client handshakes for the server [single-threaded]
    - 11 : share events that must spread for the server [single-threaded]
    - 12 : reset server counters [single-threaded]
    - 13 : send held up packets for the server [single-threaded]
    - 20 : handle all events and respond for the client [single-threaded]
    - 21 : send all events that must be synced for the client [single-threaded]
- [ 100 : 100 + number of stages [ : stage functions [parallel]
    - this is why stage functions start at 0, I didn't want to start the task IDs at 101
